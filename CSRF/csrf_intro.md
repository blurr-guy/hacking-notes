# CSRF 
---
Cross-Site Request Forgery (CSRF) is an attack that forces an authenticated user's browser to send a request to a web application they're logged into, without their knowledge or consent.


the server trusts a request just because it comes with valid cookies/session, without verifying the request was intentionally made by the user.
Browsers automatically attach cookies to every request to a domain, regardless of which site triggered that request. That's the root cause CSRF exploits.

## Target (state-changing actions):
- Account settings
	- Email address change
	- Password change
	- Phone number change
	- Security question updates
	- 2FA enable/disable (huge — CSRF here can let an attacker silently disable 2FA or add their own device)
- Financial Transactions
	- Money transfers, withdrawals
	- Adding/removing payment methods, linked bank accounts
	- Changing payout/shipping addresses
	- Placing orders, applying coupons at checkout

- Account takeover primitives
	- Add email functionality 
	- API key generation
	
- Social Content generation
	- Posting
	- Follow and unfollow mechanism

- Admin panels in organizations
	- changing role 
	- config changes
	- delete data and user credentials




## Attack scenerios of the CSRF :

### Using the html form --

Attacker craft a webpage with the hidden request set to perform CSRF

## Common defences against CSRF

- CSRF token :
	It is generated by server and stored in the client side, used when performing state-change operations.
- SameSite Cookie :
	SameSite is a browser security mechanism that determines when a website's cookies are included in requests originating from other websites
	It has Lax restriction by default.
- Referer header 
	Used to check which domain is refering the request.

- CSRF token is not tied to the user session
here application validate the token but do not authenticate it with the user session issuing it.

So we can use csrf token of one account to change the password of the another account, which results in the csrf flaw in the appliation.

- CSRF token is tied to a non-session cookie

In this the CSRF token and the session cookie are issued but they do not link with each other because they are build on the different framwork and this is where logic gets break. 
Here both session and csrf token go through validation but in different flow which is not linked with each other..

**How to actually spot this while testing**
Log in as User A, capture their session cookie + CSRF token/cookie
Open a fresh browser/incognito session (unauthenticated), grab a new CSRF cookie + token pair from that context
Take User A's session cookie, but substitute the fresh unauthenticated CSRF token/cookie into a request
If the request still succeeds → the CSRF token isn't bound to the session, just to its own cookie → vulnerable
